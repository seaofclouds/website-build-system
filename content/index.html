A build system you own.

Markdown and HTML in, a static website out. About 1,800 lines of commented TypeScript that you copy into your project and then edit until it's yours.

Use this template Read the docs

Makes you a new repo with a clean history — a copy to own, not a fork to track.

Clone it, then: 
npm install
./site
That builds the site, watches for changes, and serves it at `localhost:3000` with live reload. There's no compile step and no bundler — the TypeScript runs directly under bun, deno, or node.

Not a dependency

Part of your site

It ships in your repo, not your node_modules. Nothing is pinned elsewhere, nothing drifts, and what builds your site today builds it identically in five years.

Meant to be edited

No config file, no plugin API, no version number. You add a macro by adding a case to a switch. The extension mechanism is that you have the code.

Small enough to read

Six dev dependencies, all build-time. Nothing ships to your visitors. You can read the whole thing in an afternoon and hold it in your head afterwards.

Content like an FTP server

Put a file in content, it appears on the site at that path. Every clever behaviour beyond that is opt-in via frontmatter — and an HTML file with no frontmatter is copied through untouched.

Catches its own mistakes

Every internal link and anchor is checked against the pages just generated, so renaming a heading someone linked to gets caught at build time rather than by a reader two years later.

Fonts, feeds, and redirects

Automatic font subsetting cuts a typeface down to just the characters you use. RSS, sitemaps, llms.txt and redirect pages are generated for you, and each one is a file you can delete.

It began as the build system for [automerge.org](https://automerge.org), written by [Ivy](https://github.com/ivanreese), and was pulled out as a starting point for other sites. It's a ship of Theseus: replace a plank at a time until none of the original remains, and it's still your site's build system throughout.
